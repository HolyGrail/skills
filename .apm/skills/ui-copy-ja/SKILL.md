# 画面の日本語の文言

対象は、人に見せる短い日本語である。画面の文言のほか、通知やメールの文、告知文、資料の見出しや図の中の文も含む。以下では、まとめて「画面の文言」と書く。

画面の文言は、読み物の文章とは別の基準で書く。
読み物は読み進めてもらう文章で、画面の文言は一瞬で意味を取ってもらう文章である。
必要なのは表現の工夫ではなく、利用者がほかの画面やほかのサービスで見慣れた語を、同じ意味で使うことである。

AI が書いた文言は、次の 2 つの形で不自然になる。

- **言い換えすぎ**: 「硬い語をやわらげる」推敲を画面の文言に当て、普通に使われる漢語まで言い換える。「通知」が「知らせ」に、「確認できます」が「確かめられます」に、「プレビュー」が「見え方」になる。
- **内部の呼び名の持ち込み**: 設計や実装で使った呼び名を、そのまま利用者に見せる。「トグルを ON にすると」「最初のタブに並びます」「可変枠」「一意に決まる」「noindex 扱い」「導線を追加しました」。

## 書く前

1. プロジェクトに用語表や文言の規約があれば読む（`.claude/rules/`、`docs/`、`AGENTS.md`、glossary など）。あればそれが最優先である。
2. 書こうとしている概念を、既存の文言ファイルで検索する。同じ概念を指す語がすでにあれば、その語を使う。新しい語を選ぶのは、既存の文言に無いときだけである。
3. 既存の文言に無ければ、同じ種類のサービスで普通に使われている語を選ぶ。自分で語を作らない。新規のサービスで既存の文言が 1 つも無いときは、利用者が知っていそうな同種のサービスの画面で使われている語を基準にし、どちらの語が普通か判断できないものは、候補を並べて依頼者に選んでもらう。

## 語の選び方

- **普通に使われる漢語は言い換えない**。通知、確認、設定、表示、登録、編集、削除、解除、延長、掲載、送信、保存、変更、選択、入力、検索、公開、非公開。これらを和語に開いても読みやすくはならず、見慣れない語になる。定着したカタカナ語（プレビュー、ログイン、キャンセル、シェア）も同じで、言い換えない。漢語とカタカナ語のどちらも普通に使われるとき（通知とリマインド）は、同じ画面や置き場所のラベルで使っている語にそろえる。
- **動詞から名詞を作らない**。知らせ、確かめ、見え方、付き合い方、やり方、戻し方、食い違い。避けるのは、定着した漢語やカタカナ語があるのに、それを避けて作った名詞である。画面の語として定着しているもの（切り替え、取り消し、読み込み、受け取り、絞り込み、お知らせ）は使う。動詞のまま使うのもよい（「仲間に知らせましょう」）。「〜方」で終わる語は、「使い方」「探し方」のようにガイドの題や検索語として定着したものに限る。
- **部品は、画面に書いてある名前で呼ぶ**。トグル、スイッチ、タブの順番、セクション、ボトムシート、モーダルのような部品の種類では呼ばない。「トグルを ON にすると」ではなく「『メール通知』をオンにすると」。画面上の名前に種類の語を添えるのはよい（「『通知』タブ」）。避けるのは、種類や順番だけで指すこと（「最初のタブ」）である。
- **設計と実装の語を出さない**。導線、遷移、訴求、軸、枠、紐づく、一意、割当、成立、API、キー、noindex、フラグ。避けるのは、設計や実装の呼び名として使った場合である（「可変枠」「絞り込みの軸」「担当者の割当が成立しません」）。普通の意味で使う場合（「予約枠」「募集枠」）は当たらない。利用者ができること、利用者に起きることの言葉に直す（「導線を追加しました」→「〜から開けるようにしました」）。
- **英語の直訳と造語を使わない**。日本語として辞書や他のサービスで見ない語は、意味が通じても使わない。
- **同じ概念に 2 つの語を使わない**。「返信」と「返事」、「取り消し」と「キャンセル」、「再読み込み」と「読み込み直す」のような混在は、新しく書く側を既存の多数派に合わせる。

## 文の形

- 仕組みの説明ではなく、利用者ができることと、操作の結果を書く（「押した時点で切り替わります」→「切り替えはすぐに反映されます」）。
- エラーメッセージは、何が起きたかと、次に何をすればよいかを書く。原因が運営側の内部事情（設定漏れ、外部サービスのキー、保存容量の内訳）のときは、内部事情を書かずに「現在〜できません」と次の行動だけを書く。「時間をおいてお試しください」と書くのは、待てば直る見込みがあるときだけである。利用者の側でできることが無いときは、問い合わせ先があればそれを示し、無ければ「現在〜できません」で止める。
- 文体（です・ます、体言止め、句点の有無）は、同じ画面の既存の文言に合わせる。
- 絵文字と記号での装飾は、既存の文言に無ければ足さない。

## 書いたあと

1. 新しく書いた文言から名詞を抜き出し、それぞれを既存の文言で検索する。既存に無い名詞は、普通に使われる語か、上の「語の選び方」に当たらないかを見直す。
2. 同じ文言を引用している箇所（ガイド、ヘルプ、別画面の説明、リリースノート）を検索し、同じ語にそろえる。
3. 文言で要素を探しているテスト（E2E のセレクタなど）を検索し、合わせる。
4. 読み物用の推敲（cognitive-rhythm-writing、japanese-tech-writing、そのほかの文章を整える skill）を、画面の文言に当てない。当てると「言い換えすぎ」が起きる。リリースノートや新着情報も、画面に出る短い文なのでこちらの扱いにする。
5. 次の「別の目で点検する」を行う。

### 別の目で点検する

書いた本人は、設計や実装で使った語に慣れていて、不自然さに気づきにくい。人に見せる日本語を足したら、出す前に、書いた本人とは別の読み手に読ませる。

1. 一覧を作る。git のブランチなら、足した文言を先にコミットする（一覧に出るのはコミット済みの行だけで、未コミットの変更は出ない）。そのうえで `bash references/scripts/copy-diff.sh list`（パスはこの skill のディレクトリから見た位置。以下同じ） を実行すると、足した日本語の行が「ファイル: 文」の形で出る（Markdown、docs、テスト、コメントだけの行は除かれる）。資料や下書きのように git に無いものは、人に見せる文だけを抜き出して一覧にする。
2. 一覧を、この会話の経緯を知らない読み手（subagent）に渡す。渡すのは、一覧、このファイル、プロジェクトの用語表（あれば）、既存の文言の場所だけにする。設計の経緯や、こう書いた理由は渡さない。
3. 読み手には次の 3 つだけを尋ねる。初めて見る利用者が、意味を取れない語や見慣れない語はどれか。同じものを指しているのに、既存の文言と違う語を使っている箇所はどれか。部品や仕組みの呼び名がそのまま出ている箇所はどれか。指摘には、理由と代わりの語を付けさせる。
4. 指摘を直す。直さないと判断したものは、理由を残す。
5. git のブランチなら、直した内容をコミットしてから `bash references/scripts/copy-diff.sh mark` で点検済みと記録する。記録の前に `list` をもう一度出し、点検に出した一覧と違うのが、指摘を受けて直した行だけであることを確認する。記録は一覧の中身に結び付くので、あとで文言を足したら点検と記録をやり直す。PR の本文には、足した文言の一覧か、その件数と点検の結果を書く。

一覧の全部が人に見せない文字列（ログ、テスト用のデータ、設定ファイルの説明）のときは、点検は要らない。その判断を PR の本文に 1 行書いてから記録する。

この点検は、作業を任されて動いている subagent やセッションからでも、別の subagent に任せてよい。

### 点検を hook で担保する（任意）

点検を忘れたまま PR を出さないように、Claude Code の PreToolUse hook を同梱している（`references/scripts/copy-guard.sh`）。
登録すると、`gh pr create` / `gh pr ready` と `mcp__github__create_pull_request` の前に `copy-diff.sh check` が走り、未点検なら deny して、上の手順を返す。
足した日本語が無いとき、点検済みのとき、git リポジトリでないなど判定できないときは止めない。
登録しなくても、上の手順はそのまま使える。

登録は `settings.json` に次を足す。パスは skill を置いた場所に合わせる（例は `~/.claude/skills/` に置いた場合。プロジェクトの `.claude/skills/` に置いたなら、`command` を `"bash \"$CLAUDE_PROJECT_DIR/.claude/skills/ui-copy-ja/references/scripts/copy-guard.sh\""` にする）。
hook は自分と同じディレクトリの `copy-diff.sh` を呼ぶので、別の場所へコピーせず、skill の中のファイルをそのまま指定する。

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash|mcp__github__create_pull_request",
        "hooks": [
          {
            "type": "command",
            "command": "bash ~/.claude/skills/ui-copy-ja/references/scripts/copy-guard.sh"
          }
        ]
      }
    ]
  }
}
```

## 既存の文言を点検するとき

件数が多くなるので、次の順で進める。

1. 利用者が実際に指摘した語を集め、型に分ける（言い換えすぎ / 内部の呼び名 / 語の混在）。書き手自身の語感は当てにしない。
2. 利用者の目に入る文言を全部読む。対象は、文言ファイル、画面に直書きされた文字列、サーバーが組み立てる通知文、リリースノート。コードのコメントと、運営だけが見る画面は分ける。
3. 見つけた箇所を、指摘と同じ語 / 同じ癖から出た語 / 語の混在 / 普通の動詞（直す対象とは限らない）の段に分け、どの画面に出るかを添えて一覧にする。
4. 直す範囲を決めてもらい、変更前と変更後の対応表を見せて了承を得てから置き換える。意味が変わりうる言い換えは、その旨を添える。
5. 置き換えは、件数を確認しながら機械的に行う。想定と件数が合わない語は、同じ文言の引用が別の場所にあるので、そこも直す。

## 再び入れないために

規約と検査の両方をプロジェクトに置く。規約だけでは読み飛ばされ、検査だけでは載せた語しか止まらない。

- **用語表**: 「使う語 / 使わない語」の対応表と、このファイルの原則を、文言ファイルを編集するときに読まれる場所に置く（Claude Code なら `.claude/rules/` に、文言ファイルのパスを `paths` に指定したファイル）。
- **自動検査**: 使わない語のリストを、型チェックや CI で動く検査に入れる。文言ファイルは値だけを見て、キー名とコメントは見ない。失敗時のメッセージに、代わりに使う語を出す。直さないと決めた過去の文（古いリリースノートなど）は、その文だけを例外として記録し、新しい文には例外を作らない。
