## Phase 1: Plan (計画)

**目的**: 実装の全体像を明確にし、**GitHub issue (計画 issue) として登録して Phase 2 へ自動続行する**。計画はファイルとしてコミットしない。技術的な実装方針は Claude が自律決定し、根拠を「設計判断」節に記録する。承認待ちのための停止はしない。

**注意**: Phase 0 以降の全コマンドは `cd "$WT_PATH" && ...` または `git -C "$WT_PATH" ...` を使う。`gh issue` 系コマンドも `cd "$WT_PATH" && ...` で実行し、作業対象リポジトリに issue を作る。

### 計画の置き場所は GitHub issue (2 モード)

| 起動形態 | 計画 issue の扱い |
|---|---|
| `/dev <タスクの説明>` (新規) | 計画確定後に `gh issue create` で **計画 issue を新規作成** |
| `/dev <issue URL / #番号>` (issue 起動) | **その issue 自身を計画書として使う**。本文を読み込んで計画の下書きとし、必須節が不足していれば計画確定後に `gh issue edit` で本文を計画フォーマットに更新する |

- **計画確定前に issue を作成・編集しない**。issue の作成・本文更新はリポジトリの watcher に通知が飛ぶ外部公開操作なので、計画が確定してから 1 回で反映する (ドラフト段階で何度も編集しない)
- issue 起動モードで本文が既に計画フォーマットの必須節 (目的 / スコープ / 実装ステップ / 検証方法) を満たしているなら、本文を更新せずそのまま計画 issue として採用してよい
- issue 起動モードで本文を計画フォーマットに更新する場合、**既存の本文を黙って破棄しない**。依頼の経緯や議論が消えると文脈が失われるので、原文の要素は計画フォーマットの各節に組み込むか「## 経緯 (原文)」節として保全する

### 手順

1. **起動引数の判定**: タスク説明が issue URL または `#番号` を含む場合は issue 起動モード。`cd "$WT_PATH" && gh issue view <番号> --json title,body,url,state` で読み込み、本文を計画の下書きとして扱う (state が `CLOSED` なら AskUserQuestion で続行可否を確認 — クローズ済み issue の再着手はユーザーの意図確認が必要な稀なケース)
2. タスクの説明 (issue 起動時は issue 本文) を分析し、影響範囲を特定する
3. 既存のコードベースを調査して現状を把握する (実行主体は [model-routing.md の判定手順](model-routing.md#判定手順)で決める。数ファイルを読めば足りる調査はメイン直接、広い横断調査は `Explore` に出す)
4. **判断点を洗い出し、自律的に確定する** (後述の設計判断プロセス)
5. 実装計画を策定する (以下を含む):
   - **目的**: 何を実現するか
   - **スコープ**: 変更対象のファイル・モジュール
   - **実装ステップ**: 番号付きの具体的な作業手順
   - **検証方法**: どう正しさを確認するか
   - **リスク**: 注意すべき点
   - **設計判断**: 自律確定した判断とその根拠 (採用しなかった選択肢と却下理由も含む)
6. 計画の要点をユーザーにナレーションで提示する (**承認待ちで停止しない**。ユーザーは後から計画 issue / PR で全体を追える)
7. **計画を issue に反映する**:
   - 新規モード: 計画 issue を新規作成 (下記「計画 issue の作成コマンド」)
   - issue 起動モード: 必須節が不足していれば `gh issue edit <番号> --body-file` で本文を計画フォーマットに更新
   - いずれも投稿前に Skill(cognitive-rhythm-writing) でタイトル・本文を推敲し (人間が読む文章なので japanese-tech-writing 単独より優先。併用規範として japanese-tech-writing も読み込まれる)、`--body-file` は `mktemp` で取得、投稿直前に `head -c 300` で内容を検証する (グローバル CLAUDE.md / SKILL.md Gotchas と同じルール)
8. 計画 issue の URL をセッションファイルの `plan_issue` に記録し、**そのまま Phase 2 へ進む**

### 設計判断プロセス (計画確定前に実行)

コードベース調査後、計画を確定する前に以下を実行する。

#### Step 1: 判断点の洗い出し

調査で得た情報を元に、曖昧・未確定な箇所を列挙する:

- 技術的決定が未確定な箇所 (アプローチが複数存在)
- 競合するパターンや慣習がコードベース内に混在している箇所
- エラーケース・エッジケースの扱いが不明な箇所
- スコープの境界が曖昧な箇所
- パフォーマンス・セキュリティ・互換性のトレードオフがある箇所

#### Step 2: 判断点の分類と処理

洗い出した各判断点を **技術的判断** と **要件レベルの判断** に分類する。切り分けの目安は「これは How (どう実装するか) か、What (何を作るか) か」。How は自律決定し、What の曖昧さだけユーザーに確認する。

**技術的判断 (自律決定する)** — 以下は AskUserQuestion を使わず、自分が最適と考える選択肢を採用する:

- 実装アプローチ (複数パターンのトレードオフ比較)
- ライブラリ・フレームワーク・デザインパターンの選択
- データ設計 (スキーマ構造、API インターフェース、型定義)
- エラー・失敗シナリオの扱い (リトライ戦略、フォールバック)
- パフォーマンス最適化の程度、キャッシュ戦略
- テスト戦略 (粒度と範囲)
- 既存コードに混在するパターンのどちらに揃えるか

選定基準 (優先順):

1. **既存コードベースとの整合性** — このリポジトリのメンテナが選びそうな方を選ぶ
2. **保守性・変更容易性** — 半年後に読む人が理解しやすい方
3. **実装コストとリスクの小ささ** — 同等なら差分が小さく壊しにくい方
4. **性能** — 上記が同等のときのタイブレーク

**採用しなかった選択肢と却下理由も「設計判断」節に残す** (レビュー時に判断根拠を追える状態にする)。重大な判断は Phase 2 を待たず ADR 化してよい。

**要件レベルの判断 (このときだけ AskUserQuestion)**:

- タスク説明が複数解釈でき、どちらを選ぶかで **成果物の意味・ユーザー価値が大きく変わる** (技術的にどう作るかではなく、何を作るかの曖昧さ)
- スコープの大幅な拡大・縮小 (依頼にない機能の追加、依頼された範囲の切り捨て)
- 破壊的変更・データマイグレーションなど、**利用者に不可逆な影響**が及ぶ判断

#### Step 3: 完了判定

以下を全て満たしたら計画確定:

- [ ] 実装アプローチが 1 つに確定した (自律決定の根拠が「設計判断」節に書けている)
- [ ] スコープの境界が明確になった
- [ ] 主要なエッジケースの扱いが決まった
- [ ] 残る曖昧さが計画に影響しない程度に軽微である

### 要件確認の質の基準 (AskUserQuestion を使う稀なケース)

**確認してよい質問** (What の曖昧さ):
- 「タスク説明は X とも Y とも読めます。X なら [成果物 A]、Y なら [成果物 B] になりますが、どちらが意図ですか?」
- 「この変更は既存データの変換を伴います。旧データを [A: 移行] と [B: 切り捨て] のどちらにしますか?」(不可逆な影響)
- 「依頼範囲外ですが Z も直さないと目的が達成できません。スコープに含めますか?」(スコープの大幅拡大)

**確認してはいけない質問** (禁止):
- 技術的トレードオフの選択 (「A と B のアプローチどちらにしますか?」— 自律決定の対象。決めて根拠を記録する)
- 「この機能の目的は何ですか?」 (タスク説明に書いてある)
- 「どの言語で実装しますか?」 (プロジェクトから自明)
- 「テストは書きますか?」 (Phase 2 手順 4「スコープとテストの規律」に従って自分で決める)
- コードベースや設定ファイルを読めば分かること

### 計画 issue のフォーマット

issue のタイトルはタスクタイトル、本文は以下の構成にする。日付は issue のメタデータ (作成日時) が持つため本文には書かない。

```markdown
- **ステータス**: in-progress | completed | abandoned

## 目的

{何を実現するか}

## スコープ

{変更対象のファイル・モジュール一覧}

## 実装ステップ

1. {ステップ 1}
2. {ステップ 2}
...

## 検証方法

- {検証項目 1}
- {検証項目 2}

## リスク

- {リスク 1}

## 設計判断

{計画策定時に自律確定した判断。各判断に根拠と、採用しなかった選択肢・却下理由を付記}

- {判断 1}: {選択内容} — {根拠}。不採用: {選択肢} ({却下理由})
- {判断 2}: {選択内容} — {根拠}

## ADR

{設計判断のうち重大なものは ADR として記録。リンク一覧}

## 結果

{初期状態は空。完了後のサマリに加え、ワークフロー進行中に発生した特記事項 (`/simplify` 実行不能などの退避記録、worktree フォールバック等) もこのセクションに追記してよい。各記録には日付を添える}
```

issue 起動モードで元 issue に経緯・議論がある場合は、上記に「## 経緯 (原文)」節を足して原文を保全する。

### 計画 issue の作成コマンド

```bash
PLAN_BODY=$(mktemp -t plan-issue.XXXXXX)
cat > "$PLAN_BODY" <<'EOF'
<計画 issue フォーマットを cognitive-rhythm-writing 推敲済みの内容で埋めたもの>
EOF

# 投稿前に内容を検証 (想定する書き出しが含まれるか目視確認)
head -c 300 "$PLAN_BODY"

# gh issue create は作成した issue の URL を標準出力に返す (--json フラグは存在しない)
cd "$WT_PATH" && PLAN_ISSUE_URL=$(gh issue create \
  --title "<タスクタイトル>" \
  --body-file "$PLAN_BODY")

rm -f "$PLAN_BODY"
```

- 既存ラベルに `plan` / `planning` があれば `--label` で付与する (なければラベルなしで作成)
- issue 起動モードの本文更新は `gh issue edit <番号> --body-file "$PLAN_BODY"` を使う (mktemp + head 検証は同じ)

## Phase 2: Implement (実装)

**目的**: 計画に基づいてコードを実装する。

**注意**: 全てのファイル操作・コマンド実行は worktree (`$WT_PATH`) 内で行う。Read/Write/Edit ツールは絶対パスを使い、Bash は `cd "$WT_PATH" && ...` を先頭に付ける。

### 手順

1. 計画の実装ステップを進捗追跡の単位にする。進捗はフェーズ宣言のナレーションと計画 issue の更新で追跡し、タスク管理ツール (TaskCreate 等) が利用可能な環境ではそれも使ってよい
2. 各ステップを実行する。**着手前に [model-routing.md の判定手順](model-routing.md#判定手順)で実行主体を自律選定する** (メイン直接 / subagent + model 指定 / codex (`codex exec`)。選定理由を 1 行ナレーション)。委任時はプロンプトに `$WT_PATH`・ステップ本文・参考ファイル・完了条件を含め、依存のないステップは並列に委任する (同一ファイルを触るステップは直列)。委任成果は diff レビューと軽い検証で検収してから次へ進む
3. **設計判断が必要な場面では自律決定する**:
   - 複数のアプローチがあり計画で明示されていない場合・トレードオフがある技術的選択・仕様解釈の軽微な曖昧さは、Phase 1 の選定基準 (整合性 > 保守性 > コスト > 性能) で自分が最適と考えるものを選ぶ
   - **要件レベル (What) の曖昧さが実装中に発覚した場合のみ** AskUserQuestion を使う (Phase 1「要件確認の質の基準」と同じ線引き)
4. **スコープとテストの規律** — 実装や検証の途中で既存バグ・性能懸念・タスクに書かれていない挙動を見つけても、要求された挙動がそれ無しに成立しない場合を除き、この変更では直さず・最適化せず・拡張しない。`followups[]` に記録して PR 本文の既存問題節で報告する。タスクが曖昧なら文言と周辺コードが最も直接に支持する解釈で実装し、その仮定を計画 issue の設計判断節に書く。他の解釈のためにも作り込まない。検証は好きな方法でよいが、scratch スクリプトや一時チェックは残さない。テストをコミットするのは、タスクが求める箇所か、このリポジトリが同種の変更に既にテストを持つ箇所だけ。隣接するテストファイルと同じ規模で、明示された挙動 1 つにつき焦点の合ったテスト 1 つを目安にし、一時チェックを恒久テストに昇格させない。要求されていない抽象化・feature flag・後方互換 shim は足さない。これは追加分の話であり、タスクが求める挙動は全て完全に実装する
5. 自律決定した設計判断は ADR として記録:
   - パス: `docs/adr/{NNNN}-{slug}.md`
   - NNNN は連番 (既存 ADR の最大番号 + 1、なければ 0001)
   - ADR ファイルは worktree にコミットする (計画は issue に置き、コミットしない)
6. 計画 issue の「ADR」節にリンクを追記する (`gh issue edit <番号> --body-file`)。ADR 発生の都度ではなく **Phase 2 完了時にまとめて 1 回で更新してよい** (issue 編集のたびに推敲・検証フローが走るため)
7. 各ステップ完了時にナレーションで報告する (タスク管理ツールが利用可能ならその状態も更新する)
8. **全実装タスクが完了したら、Phase 3 へ進む前のゲートとして `/simplify` スキルを必ず実行する**:
   - 対象: 今回の変更で追加・修正されたコード
   - 目的: 再利用性・品質・効率の観点で整理し、冗長な記述や重複ロジックを解消
   - **skip 判断は禁止**。次の理由は全て skip の根拠として認められない:
     - 「差分が小さい / N 行未満」 (実例: 150 行 / 純関数 1 個 で skip → Should-fix 2 件発見)
     - 「typecheck / test / lint が PASS した」 (検証はリファクタ余地を保証しない)
     - 「リファクタ余地はなさそう」「重複や未使用コードは見当たらない」 (実装直後の主観判断は当てにならない。判定主体は `/simplify` 側)
     - 「ユーザーが急いでいる」「軽微な変更だから」「typo / 文言修正だけだから」
   - **判断主体は `/simplify` 側に固定する**: 「呼ぶか / skip するか」を Phase 2 実行者が事前判断しない。**機械的に呼んで戻り値を見る**
   - `/simplify` の戻り値が「変更なし」または書き換え適用後にのみ Phase 3 へ進む
   - simplify による書き換えが発生した場合は **自動で受け入れ、差分の要点をナレーションで報告する** (回帰は Phase 3 の Verify で検出する)
   - 書き換えが設計判断レベルの内容を含む場合は ADR に追記
   - skip してよいのは実行不能が判明した場合のみ (例: `/simplify` skill が壊れている・**未インストールで呼び出せない (Skill 実行が "skill not found" を返す)**・ユーザーが明示的に skip を指示した)。このときは skip 理由を計画 issue の「結果」節に記録し、ナレーションで報告して続行する (確認待ちで停止しない)
     - **この退避路は「機械的に呼んだが実行できなかった」場合のためのもの**。「使えなさそうだから最初から呼ばない」は skip 判断であり禁止。手順は常に「まず `/simplify` を呼ぶ → 実行不能が判明 → skip を記録して続行」の順を踏む (実行不能を理由にした skip と、事前判断による skip は別物)

### ADR ファイルのフォーマット

```markdown
# ADR-{NNNN}: {タイトル}

- **日付**: {YYYY-MM-DD}
- **ステータス**: accepted
- **関連計画**: {計画 issue の URL}

## コンテキスト

{なぜこの判断が必要になったか}

## 選択肢

### 選択肢 A: {名前}

{説明、メリット・デメリット}

### 選択肢 B: {名前}

{説明、メリット・デメリット}

## 決定

{選ばれた選択肢とその理由}

## 影響

{この決定がもたらす影響}
```

### ADR を残すべき場面

- アーキテクチャやデータ構造の設計選択
- ライブラリ・フレームワークの選定
- パフォーマンスとリーダビリティのトレードオフ
- 命名規約やパターンの決定
- スコープの削減・拡張の判断

### ADR を残さなくてよい場面

- 変数名の確認など軽微な質問
- 既にプロジェクトの規約で決まっていること
- 一時的な回避策で後から消えるもの

## Phase 3: Verify (検証)

**目的**: 実装の正しさを自動検証し、失敗があれば「新規 (今回の変更で発生)」と「既存 (main にもある)」に切り分ける。

**注意**: 全ての検証コマンドは worktree 内で実行する。`cd "$WT_PATH" && <検証コマンド>` または `git -C "$WT_PATH"` で状態確認する。

### 手順

1. プロジェクトの検証コマンドを自動検出:
   - `package.json` の scripts (test, lint, typecheck, check, build)
   - `Makefile` のターゲット (test, lint, check)
   - `mise.toml` / `.mise.toml` のタスク
   - `Cargo.toml` (cargo test, cargo clippy)
   - `pyproject.toml` / `setup.py` (pytest, ruff, mypy)
   - その他のプロジェクト設定ファイル

   **検出元コンフリクトの解決 (推測で黙って選ばない / 速さで選ばない)**: 同一の論理チェック (例: `test`) が `package.json` / `Makefile` / `mise.toml` など複数の検出元で定義され、中身が食い違うことがある (例えば `pyproject.toml` は `pytest -q`、`Makefile` の `test:` は `pytest --cov && behave`、`tox.ini` は `tox -e py311,integration` を呼ぶ、というように粒度・範囲が異なる場合)。どれを Phase 3 で走らせるかを当てずっぽうで決めたり、黙って 1 つに倒したり、「一番速いもの」で機械的に絞ったりしない。**速さではなく「プロジェクトが意図した PR ゲート (canonical)」を優先する**。次の手順で判断する:

   1. **canonical な検証コマンドを特定する**。「メンテナがこのプロジェクトの正規の検証として意図しているのはどれか」を、当てずっぽうではなく根拠を持って見極める。手がかり (上から順に強い):
      - CI 設定 (`.github/workflows/*.yml`, `.gitlab-ci.yml` 等) が実際に呼んでいるコマンド = メンテナが PR ゲートとして意図しているものに最も近い
      - `CONTRIBUTING.md` / `README` / プロジェクトの `CLAUDE.md` が「テストはこれで回す」と明記しているもの
      - `Makefile` の `test:` のように、ラッパーが複数チェックを束ねている場合、それがプロジェクトの「フルの検証」を表す意図である可能性が高い (速さを理由に内側の 1 つだけに勝手に縮めない)
   2. **canonical なコマンドを Phase 3 で実行する**。ただしその中に **worktree 内で完結しない要素** (ブラウザ E2E (playwright 等)・staging/本番や外部サービスへの到達・実機必須項目) が含まれる場合は、その重い/外部依存の要素**だけ**を切り出して Phase 5 の Test plan の「人手必須 / CI 項目」に回す (線引きは [phases-5-6.md Test plan 構築ルール](phases-5-6.md#test-plan-構築ルール) と同じ)。**「速いから」「ローカルで完結するから」を理由に canonical なチェックの中身を縮めるのは禁止** — 縮めてよいのは「worktree 内で物理的に実行できない要素」に限る。
   3. 採用した canonical コマンドと、Phase 5 に分離した要素・その理由を **ナレーションおよび PR body の検証結果メモに明記する** (後から「なぜこのコマンドを選んだか」を追える状態にする)。
   4. **canonical が一意に特定できない場合は、検出された論理チェックの和集合を実行する**: CI 設定も慣習ドキュメントも無く、複数の検出元が同格に見えてメンテナの意図が判別できないときは、重複を除いた全ての論理チェック (型 / lint / テスト / ビルド) を実行し、和集合を採用した旨と各検出元を記録する。ユーザー確認のために停止しない (過剰に検証する分には安全側)。

2. 検出したコマンドを以下の順序で実行:
   1. **型チェック** (tsc, mypy, cargo check 等)
   2. **Lint** (eslint, ruff, clippy 等)
   3. **テスト** (jest, pytest, cargo test 等)
   4. **ビルド** (npm run build, cargo build 等)
3. 検証コマンドが見つからない場合は、言語標準のコマンド (例: `npx tsc --noEmit`, `cargo check`, `python -m pytest`) を試み、それも無ければ「このリポジトリに検証手段なし」と記録して続行する (PR body の検証結果に明記。憶測でコマンドを捏造しない)
4. **失敗があれば「新規 vs 既存」を切り分ける** (次の手順)
5. 結果をサマリーで報告 (種別を明示)

### 失敗時の切り分け手順 (重要)

検証で 1 件でも FAIL があった場合、**default ブランチが checkout された別の worktree で再実行する**。worktree 方式では stash も checkout も不要で冪等に比較できる。

#### 1. default ブランチの worktree を探す

```bash
MAIN_WT=$(git -C "$REPO_ROOT" wt --json \
  | jq -r --arg b "$DEFAULT_BRANCH" '.[] | select(.branch == $b) | .path')
```

`MAIN_WT` が空でなければケース A、空ならケース B に進む。

#### 2. ケース A: `MAIN_WT` が見つかった場合 (通常)

- FAIL した検証コマンドをその worktree で再実行:
  ```bash
  cd "$MAIN_WT" && <failing-command>
  ```
- この `cd` は次の Bash 呼び出しにも残りうる (メインセッションの既定)。切り分け後のコマンドは `cd "$WT_PATH" && ...` を付けて作業中の worktree で実行する
- worktree は独立しているので、作業中の変更に影響を与えない (stash 不要、冪等)
- `MAIN_WT` が古い可能性があれば `git -C "$MAIN_WT" pull --ff-only origin "$DEFAULT_BRANCH"` を実行してから切り分ける (ff-only は fast-forward できないとき失敗するだけで作業を壊さないので確認不要)

#### 3. ケース B: `MAIN_WT` が見つからない場合 (フォールバック)

- `$REPO_ROOT` 自体のブランチが default ブランチなら `MAIN_WT="$REPO_ROOT"` としケース A に戻る
- それ以外は **一時的な main 用 worktree を自動作成して切り分ける**。作成: `git -C "$REPO_ROOT" wt --nocd _main-verify "origin/$DEFAULT_BRANCH"`。パス取得は Phase 0 手順 7 と同様 `wt --json | jq` で引く。検証後に `git -C "$REPO_ROOT" wt -D _main-verify` で削除する (この worktree は切り分けのために今作った使い捨てなので `-D` してよい — Phase 6 の `-D` 禁止ルールの対象外)

#### 4. 結果の判定

- `MAIN_WT` でも同じエラー → **既存問題** (main 由来、今回の変更とは無関係)
- `MAIN_WT` では出ない → **新規問題** (今回の変更で発生)

### 禁止事項

worktree 内で `git checkout <他のブランチ>` を使った切り分けは行わない (作業状態を壊すリスク、stash pop コンフリクトの手間が再発)。必ず別 worktree で再実行。

### 検証結果のサマリー形式

表の各行は、このセッションで実際に実行したコマンドとその結果に対応させる。未実行の項目は「未検証」と明示する (報告は証拠に対応させる — SKILL.md「全フェーズ共通」6)。

```
## 検証結果

| チェック | コマンド | 結果 | 種別 |
|---------|---------|------|------|
| 型チェック | tsc --noEmit | PASS | - |
| Lint | eslint . | FAIL (3 errors) | 新規 (今回の変更で発生) |
| テスト | npm test | FAIL (1 test) | 既存 (main にも存在) |
| ビルド | npm run build | PASS | - |
```

「既存」が含まれる場合は Phase 4-B の自動判断マトリクスで対応を確定する。

## Phase 4: Fix (修正)

**目的**: 検証で発見された問題を、種別に応じた方針で対応する。

### 4-A. 新規問題 (今回の変更で発生)

1. 失敗内容を分析
2. 問題を修正する
3. 該当する検証コマンドを再実行する
4. 修正 → 再検証ループを解決まで回す。ただし **3 回で解決しなければ修正の積み重ねを止め、根本原因の診断に切り替える** — 失敗理由を説明できる状態にしてから次の修正に入る (試行錯誤の連打は差分を汚し、原因を見失う)
5. 根本原因を特定してもなお自力で解決できない場合 (外部サービス・権限・環境設定など自分では動かせない要因に行き着いた場合) のみ、診断結果と試したことをまとめてユーザーにエスカレーションする

### 4-B. 既存問題 (main にも存在)

main 由来の問題は独立した課題として扱う。**次の自動判断マトリクスで対応を確定し、判断と根拠を PR 本文に明記する** (確認待ちで停止しない。黙ってスルーもしない):

| 条件 (上から順に評価) | 対応 |
|---|---|
| その問題が **CI を落とす** (Phase 5.5 の「CI 全成功」が達成不能になる) | **今回 PR で併せて修正** (別コミット `fix: ...` として残す) |
| CI は通るが、修正が小さく (目安: 数ファイル・数十行) 今回の変更と関連が深い | 今回 PR で併せて修正 (別コミット) |
| 修正が大きい / 関連が薄い / 専門知識・追加調査が必要 | **`followups[]` に `decision: "separate-pr"` で追記** し、PR 説明に「既存問題は別 PR で対応予定」と明記 (Phase 6 で自動 issue 化) |
| 対応する価値が低いと判断できる根拠がある (廃止予定コード等) | **`followups[]` に `decision: "out-of-scope"` で追記** し、PR 説明に「main 既存の課題、本 PR では対応しない」と明記 (Phase 6 で自動 issue 化) |

判断に迷ったら `separate-pr` (followup 化) に倒す。今回 PR で修正するのは「入れないと CI が通らない」か「安いから拾う」場合に限る (スコープ膨張を防ぐ)。

### followups[] への記録

セッションファイル `~/.claude/dev-sessions/<slug>.json` の `followups[]` に追記:

```json
{
  "title": "main にも存在する型エラー (mypage.test.ts の 2 箇所) を修正",
  "body": "PR #131 で混入した型エラーが mypage.test.ts line 42, 58 に残存。今回 PR のスコープ外として持ち越し。検証ログ: <貼り付け>",
  "decision": "separate-pr",
  "source": {
    "kind": "existing-verification-failure",
    "command": "npm test",
    "files": ["mypage.test.ts"]
  },
  "created_at": "<ISO 8601 now>",
  "issue_url": null
}
```

- `title`: 1 行サマリ (そのまま issue title になる)
- `body`: issue 本文の素材。検証結果の抜粋、影響範囲、再現手順
- `decision`: `"separate-pr"` or `"out-of-scope"`
- `source`: 何の検査で発見したか
- `issue_url`: Phase 6 で issue 化された時に URL を記録 (再実行冪等性のため)

### 判断例 (ナレーションで報告する)

```
main にも存在する型エラー (mypage.test.ts の 2 箇所、PR #131 で混入) を検出しました。
CI の typecheck ジョブを落とすため、自動判断マトリクスに従い今回 PR で
別コミット (fix: ...) として修正します。
```

### 完了条件

以下のいずれかを満たしたら Phase 5 へ進む:

- 全検証が PASS している
- 新規問題は全て解消、かつ既存問題は自動判断マトリクス (修正 / separate-pr / out-of-scope) で明示対応済み

### 禁止事項

既存問題を記録なしに「スルー」して PR を作らない。「main にもあるから無視」は NG。必ずマトリクスに掛けて「今回修正」か「followup 化 + PR 本文に明記」のどちらかを明示する。
