# Model Routing: 作業単位の実行主体を自律選定する

メインセッションは**司令塔** (計画・判断・統合・検証判定・外部公開操作) に徹し、各作業単位はメイン直接を含めて「誰にやらせるのが総コスト最小か」で振り分ける。**固定の対応表は置かない** — どの実行主体を使うかは、以下の判断原則と実行主体カタログを踏まえてメインがタスクごとに自律判断し、選定理由を 1 行ナレーションする。SKILL.md 本体から「Phase 1 の調査を委任するとき」「Phase 2 / 5.5 の実装ステップを委任するとき」に参照する。

## 判断の原則

1. **その作業を確実にこなせる最小コストの実行主体を選ぶ** — 過剰なモデルはトークンの無駄、過小なモデルはやり直しで結局高くつく。「安い方に倒す」ではなく「確実にこなせる範囲で最小」
2. **メイン文脈に載せる情報を最小化する** — 大量のファイル読み込み・広い探索・長いログを伴う作業は、結論だけ戻せる形に切って下ろす。メイン文脈の消費はどのモデルより高くつく
3. **検収コストを織り込む** — 成果の検証が難しい・やり直しが高くつく・誤りに気づきにくい作業ほど、上位モデルまたはメイン直接に寄せる。検収が安い作業 (型チェックで機械的に判定できる等) は下位モデルに下ろしやすい
4. **委任オーバーヘッドと比較する** — 委任にはプロンプト作成・検収・往復のコストが常にかかり、subagent は文脈を作り直して探索し直す。数回のツール呼び出しで済む作業 (数ファイルの読み込み、少数の編集、単純な検索)、直前の文脈と密結合な作業、検証や見直しはメイン直接。並列に委任するのは独立して規模のある作業 (別モジュールの実装、広い横断調査) だけで、小さな作業を分割して並べない
5. **決めかねたら先へ進む** — 材料が揃わなければメイン直接か 1 段上のモデルを選ぶ

## 実行主体カタログ

選択肢とその特性。**「この種の作業はこの主体」という固定規則ではない** — 判断の材料として使う:

| 実行主体 | 特性 | 相対コスト | 注意 |
|---|---|---|---|
| `Agent` + `model: haiku` | パターンが明確な検索・列挙・機械的作業に十分 | 最小 | 統合・要約・判断の質は期待しない。取りこぼしのリスクを検収コストと天秤にかける |
| `Agent` + `model: sonnet` | 調査結果の統合、手順が明確な実装、定型修正 | 小 | 設計判断の余地が大きい作業では精度が落ちる |
| `Agent` + `model: opus` | 複数ファイル整合、設計判断を含む実装、精度が要る調査 | 中〜大 | メインが Opus 系なら model 未指定と同等で、コストは下がらない |
| `Agent` + model 未指定 (= メインと同格) / `fork` | メイン級の判断力が要るが、出力をメイン文脈から隔離したい作業 | 大 | `fork` は文脈を継承する (横断的な重い読み込み向き) |
| codex (`codex exec`) | 要件明確な自己完結ユニットの自律実装。別系統のフロンティアモデル | **Claude トークンを消費しない別枠** | model は `~/.codex/config.toml` に従う。[dev 固有ルール](#codex-呼び出しの-dev-固有ルール)参照 |
| メイン直接 | 判断・統合・軽微な編集・密結合作業 | メイン文脈を直接消費 | 委任オーバーヘッドが利得を上回るときの正解 |

agent type は作業の性質で選ぶ (調査 = `Explore`、実装 = `general-purpose`、診断 = `analyzer` 等。グローバル CLAUDE.md「委任」の方針に従う)。model 指定は Agent ツールの `model` パラメータで行う (このリポジトリの `~/.claude/agents/*.md` は model 未指定なので、パラメータ指定がそのまま効く)。

Codex の位置づけ: コスト序列の一段というより「**Claude のトークン予算の外にある自律実装力**」。実装経路の探索・設計から任せられる自己完結単位を切り出せるなら、トークン効率の観点で有力な選択肢になる。ただし検収 (diff レビュー) はメインの仕事として残るので、検収しづらい作業を丸投げする先ではない。

## 判定手順

各作業単位の着手前に:

1. **委任する価値があるか** — 原則 1・2・4 で評価する。軽微・密結合・委任プロンプトを書く方が高くつく作業はメイン直接
2. **委任するなら実行主体を選ぶ** — 作業の性質 (調査 / 実装 / 診断)、要求される判断力、検収のしやすさから、カタログを材料に選定する
3. **選定理由を 1 行ナレーションする** — 「このステップは◯◯なので△△ (model: ×) に委任」。追跡可能性のためで、長い説明は不要

### 例 (目安であって固定規則ではない)

- 単純な所在特定の横断検索 → `Explore` + haiku で足りることが多い
- 構造・影響範囲の把握 → `Explore` + sonnet が目安
- やることが確定した実装ステップ → `general-purpose` + sonnet、整合や設計判断を含むなら opus
- 要件明確・自己完結で実装経路の探索から任せる単位 → codex

ただし逆転は普通にありうる: 検索対象の命名が揺れていて判断が要る横断調査は haiku では取りこぼすので sonnet 以上に上げる、逆に「対象ファイル 1 個の明確な修正」は委任せずメイン直接が最安、など。**例の表面 (作業の種類) ではなく判断の原則 (確実性 × コスト × 検収) で決める**。

## 委任プロンプトの必須要素

subagent / codex への委任プロンプトには以下を**全て**含める。欠けると worktree 外汚染・規約違反・往復のやり直しが起きる:

1. **`$WT_PATH` の絶対パス** + 「この worktree 外のファイルを読み書きしない」
2. **該当ステップの内容そのもの** (計画 issue の番号だけでなく本文を貼る。subagent は issue を読める保証がなく、読ませるとトークンも無駄)
3. **従うべき既存規約の具体例** (参考にすべき既存ファイルのパス 1〜2 個)
4. **完了条件**と、実行してよい検証コマンド (該当ステップに閉じたもの。フル検証は Phase 3 でメインが行う)
5. **「コミット・push・`gh` 操作はしない。ファイル編集まで」** (責務の固定。次節)
6. **スコープの規律**: タスクに書かれていない既存バグ・改善点は直さず報告に回す。テストはタスクが求める箇所か既存テストがある種類の変更だけ、隣接ファイルと同じ粒度で。scratch の確認を恒久テストにしない。不要な抽象化・flag・shim を足さない (全文は [phases-1-4.md Phase 2 手順 4](phases-1-4.md#phase-2-implement-実装))

## Codex 呼び出しの dev 固有ルール

グローバル CLAUDE.md「Codex CLI」の呼び出し規約 (`codex exec`) に従った上で、dev では以下を上書き・追加する:

- **`-C "$WT_PATH"` を指定する** (リポジトリ root ではない。worktree 外で作業させない)
- **`model`: 指定しない** (`~/.codex/config.toml` の `model` 設定に従う。バージョン名をスキルにハードコードしない)
- `-s workspace-write` (規約どおり)。worktree の gitdir は sandbox の書き込み範囲外なので、codex は git の書き込み操作ができない。コミットはもともとメインの責務なので問題にならない
- `prompt` は英語で、[委任プロンプトの必須要素](#委任プロンプトの必須要素) を全て含める
- 続きの指示は `cd "$WT_PATH" && codex exec resume <thread_id>` で同一会話に送る (新規呼び出しで文脈を捨てない)。thread_id はセッションファイルではなく、その作業単位の間だけ手元に持つ
- 実装ステップは数分を超えやすいので `run_in_background: true` で起動し、完了通知を待つ間に依存しない作業を進める
- **`codex exec` が利用不能な環境** (codex 未導入・未ログイン・呼び出しエラー) では、その作業単位を[判定手順](#判定手順)で振り分け直し (`Agent(general-purpose)` かメイン直接)、その旨をナレーションで報告する

## 委任しても移らない責務

以下は**常にメインが行う**。subagent / codex に代行させない:

- コミット・push・PR / issue の作成・編集 (cognitive-rhythm-writing 推敲を含む)
- セッションファイル (`~/.claude/dev-sessions/<slug>.json`) の更新
- Phase 3 の検証実行と PASS / FAIL・新規 vs 既存の判定
- Phase 2 末尾の `/simplify` ゲート実行
- ADR の最終記録 (subagent / codex が報告した設計判断を素材に、メインが採否を判断して書く)
- Phase 5.5 の triage・返信・エスカレーション判断

## 検収とエスカレーション

- **委任成果は必ず `git -C "$WT_PATH" diff` で diff レビューしてから受け入れる**。委任先の「完了しました」報告を鵜呑みにしない (グローバル CLAUDE.md 委任節の確認ルール)
- 受け入れ後、該当ステップに閉じた軽い検証 (型チェック等) をメインで実行してから次のステップへ進む
- **委任成果が検証 FAIL したら、同じ実行主体に同じ形で再委任しない**。原因が能力不足なら 1 段上のモデルに上げるかメインで引き取り、プロンプト不備なら不足を補って再委任する
- **同一ステップで 2 回連続 FAIL したら、3 回目の委任はせずメインが直接引き取る** (往復でトークンを溶かさない。Phase 4-A の「3 回で根本原因診断に切替」より手前で損切りする)
- スコープ外の変更が混入していた場合は、その部分を revert してから受け入れる (「ついでの修正」を黙って取り込まない)

## 並列化

- 依存のない調査・実装ステップは **1 メッセージで複数 Agent を同時起動**する (順次委任しない)
- ただし**同一ファイルを触るステップは直列化する** (同じ worktree 内で編集が衝突する)
- codex は 1 worktree につき同時 1 会話まで (workspace-write が同じツリーに並ぶと衝突する)
- 委任した subagent の完了を待つ間、依存しない作業 (次ステップの委任プロンプト作成、セッションファイル更新、計画 issue 本文の下書き) を進める。結果は通知で届く

## フェーズ別の委任ポイント

| フェーズ | 委任候補 (実行主体は判定手順で都度選定) | メインに残るもの |
|---|---|---|
| Phase 1 | コードベース調査 (`Explore` 等) | 設計判断・計画確定・issue 化 |
| Phase 2 | 実装ステップ | `/simplify` ゲート、ADR 記録、コミット |
| Phase 3 | 原則委任しない | 検証実行・PASS / FAIL 判定・切り分け |
| Phase 4 | 根本原因診断で調査範囲が広い場合の `analyzer` | 修正方針の確定・修正ループの制御 |
| Phase 5.5 | CI FAIL・レビュー指摘 (`fix` 分) の修正実装 | triage・返信・push・baseline 管理 |
