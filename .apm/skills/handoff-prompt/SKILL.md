# Handoff Prompt

いま進めている作業を、会話履歴を持たない相手に渡すための文章を作る。相手は別の OS の PC かもしれないし、新しい Claude Code セッションや Codex かもしれない。共通するのは、この会話で分かっていることを相手は何も知らないという一点で、引き継ぎ文の良し悪しはそこで決まる。

同じ環境で同じセッションを再開するなら `/dev resume` を使う。本 skill は環境かセッションが変わるときのためのもの。

## 使い方

```bash
/handoff-prompt                          # 現セッションの作業を引き継ぐ文を生成
/handoff-prompt windows                  # 渡し先の環境を指定 (前提節が変わる)
/handoff-prompt codex                    # Codex に渡す (英語で生成)
/handoff-prompt "issue #66 の 3 項目目"   # 渡す範囲を絞る
```

- 引数なし: 現セッションで最後に触っていた作業を対象にし、渡し先は「別の Claude Code セッション (同じ OS)」とみなす
- 渡し先の指定: `windows` / `mac` / `linux` / `codex` / `cloud`。前提節の OS とツールの書き方、パス区切り、シェルの流儀が変わる
- 範囲の指定: issue の項目や機能名で絞る。絞らないと現セッションの残作業を全部渡す文になる

## 必須節

次の 7 節をこの順で必ず入れる。該当が無い節も「なし」と書いて残す。節ごと消すと、相手は「書き忘れ」と「本当に無い」を区別できない。

| 節 | 書くこと | 典型的な抜け |
|---|---|---|
| 目的 | この作業が何のためにあるか。issue か計画があれば URL | 手段 (「〜を実装する」) だけ書いて、なぜが無い |
| 現状 | ブランチ名、PR の URL と状態、未コミットの変更の有無、直近の検証結果 (何を実行して何が通り何が落ちたか) | 「だいたい動く」。どのコマンドで確かめたかが無い |
| 次にやること | 着手する順に番号付き。各項目に触るファイルを添える | 1 行目が「まず状況を把握して」になっている |
| 検証手順 | 実行するコマンドと、通ったと判断する基準 | テストの名前だけで、起動方法が無い |
| 完了条件 | 何をもって終わりとするか。PR を出すのか、マージまでか、報告だけか | 「完了したら教えて」で止まっている |
| 報告形式 | 終わったら何を、どこに、どの形で返すか (PR URL、コミット SHA、ノートファイルの場所) | 報告先が無く、結果が相手のセッションに閉じる |
| 前提 | OS、必要なツールとバージョン (例: Node 20 以上、ffmpeg が PATH にある)、リポジトリの取得手順、必要な環境変数の名前と取得手段 | 自分の環境にあるものを相手にもあると思い込む |

## 書き方の規則

相手は会話履歴を持たない。規則はどれもそこから出ている。

- **指示語を使わない**：「上記」「先ほど」「さっきの」「この件」は、相手には何も指さない。毎回その対象を名前で書く
- **ファイルは絶対パスかリポジトリ相対で書く**：「設定ファイル」ではなく `src-tauri/tauri.conf.json`。Windows に渡すときはリポジトリ相対に寄せ、クローン先のパスは前提節で 1 回だけ書く
- **issue と PR は URL で書く**：`#66` は同名リポジトリが複数あると迷う。`https://github.com/owner/repo/issues/66` と書く
- **推測は「未確認」と印を付ける**：自分で確かめていない経緯や原因には `(未確認)` を付ける。相手が推測を事実として前提にすると、間違っていたときの手戻りがもっとも大きい
- **秘密の値を書かない**：API キー、トークン、パスワードは値を書かず、名前と取得手段だけ書く (「`OPENAI_API_KEY` を 1Password の "otelop dev" から」)。`.env` の中身も貼らない
- **コマンドはそのまま実行できる形で**：プレースホルダを残さない。残すなら `<PR番号>` のように囲い、前提節で何を入れるか書く
- **判断の理由を 1 行添える**：「A ではなく B で進める。A は〜で詰まった」。理由が無いと相手は A をやり直す
- **やらないことも書く**：スコープ外にした項目、触ってはいけないファイル、別 PR に回した変更

## 生成手順

現状節と次にやること節は、記憶ではなく、生成の直前に実行したコマンドの出力から埋める。会話の途中で push や検証が入り、覚えている状態と手元の状態がずれていることが多い。

1. **git の状態を取る**

   ```bash
   git branch --show-current
   git status --short
   git log --oneline -5
   git fetch -q
   git log --oneline '@{push}..HEAD'          # 未 push のコミット (push 先の追跡ブランチと比べる)
   ```

   未 push の判定は push 先 (`@{push}`、通常は `origin/<branch>`) と比べる。`origin/main..HEAD` と比べると、push 済みの feature ブランチでも全コミットが未 push に見える。`@{push}` が無い (upstream 未設定か一度も push していない) ときは `git log` がエラーを返すので、現状節には「リモートブランチなし。全コミットが未 push」と書く

2. **PR と issue を取る**

   ```bash
   gh pr view --json url,state,isDraft,title,statusCheckRollup 2>/dev/null
   gh issue view <番号> --json url,title,body     # 範囲指定が issue のとき
   ```

   issue のチェックリストを渡すときは、どの項目が済み (`[x]`) でどれを渡すのかを本文から読んで書く

3. **直近の検証結果を集める**：このセッションで最後に実行したテスト、lint、build のコマンドと結果。実行していなければ「未実行」と書く。通ったと記憶していても、コミット後に実行していなければ「コミット前に実行、コミット後は未実行」と書く

4. **前提を洗い出す**：リポジトリの `mise.toml` / `.tool-versions` / `package.json` の `engines` / `rust-toolchain.toml` からツールとバージョンを拾う。渡し先が別 OS なら、現 OS 固有のコマンド (`sed -i ''`、`open`、`pbcopy`) が手順に混ざっていないかを見る

5. **テンプレートに流し込む**：下の型に沿って 1 ブロックで書く。長さの目安は 30〜60 行。60 行を超えるなら、渡す範囲を絞るか、詳細を共有ノートのファイルに逃がして URL かパスで指す

6. **読み返す**：「上記」「先ほど」「この」を検索して消す。`#数字` だけの参照を URL にする。推測の箇所に `(未確認)` が付いているか、秘密の値が混ざっていないかを見る

## 出力の型

次の 1 ブロックをそのまま返す。見出しは固定、中身は現セッションの値で埋める。

````markdown
# 引き継ぎ: <作業名>

## 目的
<何のための作業か 1〜2 文>。計画: <issue / PR の URL>

## 現状
- リポジトリ: <URL>、ブランチ `<branch>` (origin に push 済み / 未 push <n> コミット)
- PR: <URL> (<Draft / Open / なし>)、CI: <通過 / 失敗 <job名> / 未実行>
- 未コミットの変更: <なし / あり: <ファイル>>
- 直近の検証: `<コマンド>` → <結果> (<いつ: コミット <sha> の時点>)
- 経緯: <判断とその理由を 1〜3 行。確かめていないものは (未確認)>

## 次にやること
1. <作業> (触るファイル: <path>)
2. <作業> (触るファイル: <path>)
3. ...

やらないこと: <スコープ外、触らないファイル、別 PR に回したもの>

## 検証手順
```bash
<セットアップがあればそのコマンド>
<テスト / lint / build のコマンド>
```
通ったと判断する基準: <出力の何を見るか>

## 完了条件
- <PR を Draft で出す / 既存 PR に push する / 報告のみ>
- <成果物の場所>

## 報告形式
<PR URL とコミット SHA を返す / 共有ノート <path> に書く / 画面の文字列で返す>

## 前提
- OS: <Windows 11 / macOS / Linux>、シェル: <PowerShell / zsh>
- ツール: <Node 20 以上>、<ffmpeg が PATH にある>、<gh CLI でログイン済み>
- リポジトリ取得: `git clone <URL>` → `git switch <branch>`
- 環境変数: `<NAME>` (値は <取得手段>。この文には書かない)
````

Codex に渡すときは同じ節構成を英語で書き、`## 前提` に作業ディレクトリと sandbox の条件 (`workspace-write` など) を足す。

## 注意事項

- **生成前に git と gh を実行する**：現状節を記憶で埋めない。ブランチ名、push 済みか、PR の状態は毎回取り直す
- **未確認を未確認と書く**：原因の推測、他人の作業の状況、「たぶん通る」は印を付ける。相手が確かめ直せるように、確かめ方も添える
- **秘密の値を書かない**：トークンや鍵の値、`.env` の中身は、引き継ぎ文にもノートにも載せない
- **1 ブロックで返す**：相手がコピーして貼れることが条件。説明や前置きを文の外に書き、ブロックの中には引き継ぎ文だけを入れる
- **長くしすぎない**：30〜60 行。超えるなら範囲を絞る。経緯を全部書くより、次の 3 手と確かめ方が正確なほうが相手は動きやすい
- **渡したあとの連絡先を書く**：相手が詰まったときに誰に、どこで聞くか (共有ノートのパス、issue のコメント)

## 実行例

```
# Otoawase (Tauri) の Windows 側作業を渡す
/handoff-prompt windows "issue #66 の 3 項目目"

# 期待される動作
# 1. git branch / status / log、gh pr view、gh issue view 66 を実行
# 2. issue #66 のチェックリストから 3 項目目の本文と、1〜2 項目目が [x] であることを確認
# 3. 前提節を Windows 向けに書く (PowerShell、Rust toolchain、WebView2、Node のバージョン)
# 4. 「# 引き継ぎ: ...」から始まる 1 ブロック (30〜60 行) を返す
#    → ユーザーがそのまま Windows PC の Claude Code に貼る

# 別セッションに続きを渡す
/handoff-prompt
```

## 関連スキル

- `/dev resume` : 同じ環境で同じセッションを再開するとき (引き継ぎ文は不要)
- `/pr-create` : 引き継ぎ前に手元の変更を PR にしておくとき
- `/release` : 渡す作業がリリースなら、提出物一覧をそのまま「次にやること」に使える
